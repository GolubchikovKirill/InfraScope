# InfraScope: производительность, сеть, интерфейс и структура кода (октябрь 2026)

Продолжение [аудита сентября](platform-audit-2026-09.md): там закрыты эксплуатация,
рантайм и асинхронный опрос принтеров. Здесь — то, что осталось на пути запроса и
опроса, интерфейс и крупные файлы. Всё проверено локально: `ruff`, 599 тестов
бэкенда, 247 тестов фронтенда, `tsc`, сборка Vite, снимки экрана в светлой и тёмной
теме на десктопе и телефоне. На проде ничего не запускалось.

## 1. Бэкенд и сеть

### Кэш списков (`app/services/cache.py`)

Списки принтеров, свитчей, касс, компьютеров, медиаплееров, логов и ML-прогнозов
кэшируются в Redis на 10–30 с. Было две проблемы.

**Инвалидация была O(всех ключей Redis).** `invalidate_entity_cache` обходил
keyspace через `SCAN printers:*`. В той же базе лежат локи, rate-limit, чёрный
список JWT и состояние circuit breaker'а по каждому устройству. Инвалидация
срабатывает на каждый цикл опроса каждой категории и на каждую правку.
Теперь у каждого пространства имён один hash `cache:<namespace>`, а варианты
запроса (фильтр/страница) — его поля. Сброс — один `DEL`, запись — один
pipeline `HSET` + `EXPIRE NX`. TTL ставится один раз при создании hash'а, поэтому
ни одна запись не живёт дольше TTL.

**Попадание в кэш стоило почти как промах.** Байты из Redis разбирались в
Pydantic-модели, после чего FastAPI валидировал их по `response_model` и
сериализовал заново. Теперь `EntityCache.get_response()` отдаёт сохранённый JSON
готовым `Response`. При промахе модель сериализуется один раз с `by_alias=True`,
как это делает сам FastAPI, так что тела ответов при попадании и промахе
совпадают байт в байт (это проверяет тест).

**Гонка с realtime.** Раньше событие `invalidate` уходило в WebSocket раньше, чем
удалялись ключи. Браузер, успевший перезапросить список в этот промежуток,
получал старую страницу и держал её до следующего изменения. Теперь порядок
обратный.

### Опрос принтеров (`app/services/snmp/`)

- В `poller.py` «стратегия 4» и «стратегия 5» были одним и тем же вызовом
  `_get_toners_via_http`. Для принтера без веб-панели это два прохода по
  2 URL × http/https × 8 с таймаута на каждом полном цикле. Второй проход удалён.
- `_tcp_reachable` проверял порты 80/443/9100/631 последовательно с таймаутом
  2 с, и офлайн-принтер занимал рабочий поток на 8 с. Теперь все соединения
  открываются неблокирующими сокетами разом и ждутся одним `selectors`: ответ
  приходит при первом открытом порту, а молчащий хост стоит один таймаут.
  Адрес резолвится через `getaddrinfo`, IPv6 работает как раньше.

### Соединения и event loop

- `_fill_mac_in_background` (поиск MAC после создания или правки принтера)
  держал открытую `Session` и, значит, соединение из пула все ~20 с SNMP- и
  ping-таймаутов. Несколько правок подряд выбирали пул (`DB_POOL_SIZE`) для всех
  запросов. Теперь: прочитать → закрыть → искать в сети → открыть заново и записать.
- `get_current_user` (каждый авторизованный запрос) и рукопожатие WebSocket
  читают пользователя из БД через `run_in_threadpool`, а не блокирующим вызовом
  внутри event loop.
- `ConnectionManager.broadcast_local` отправлял сообщения клиентам по очереди.
  Уснувший ноутбук на Wi-Fi задерживал обновления всех вкладок и вместе с ними
  цикл Redis-relay. Теперь отправка идёт через `asyncio.gather` с таймаутом 5 с на
  клиента; клиент, не уложившийся в таймаут, отключается.

### База данных

Миграция `926a321779de`: индекс `ix_eventlog_kind_type_created`
(`device_kind, event_type, created_at, device_name`). Его использует подсчёт
офлайн-событий за 24 часа, который выполняется в каждом ответе со списком
принтеров. Таблица только растёт. Миграция применяется сама при старте
(`scripts/prestart.sh`).

### Nginx

Добавлены `gzip_proxied any` и `gzip_vary on`. По умолчанию nginx не сжимает
ответы на запросы с заголовком `Via`. По наблюдениям прошлого аудита
корпоративный шлюз `vnk-srv-gate01` проксирует трафик, и если он ставит `Via`,
JSON со списками уходил несжатым.

## 2. Фронтенд

### Карточки принтеров

Страницу просматривают в поисках магазина («где кончается тонер»), а не модели:
бо́льшая часть парка — три-четыре модели. Поэтому магазин стал заголовком
карточки: 17 px, полужирный, до двух строк, полное имя в `title`. Модель с
маленькой иконкой типа устройства ушла во вторую строку. IP и ПК собраны в одну
строку метаданных. Плашка «Нестабильная связь» вынесена в отдельную строку:
под бейджем статуса она сжимала заголовок до «Brother …». Так же устроены
карточки этикеточных принтеров.

### Тёмная тема

Что было не так (по снимкам экрана):

1. Все слои — фон, карточки, меню, активные пункты, кнопки — одного тёмно-синего
   тона. Акценту не на чем выделиться, карточки сливаются с фоном.
2. Цвета Tailwind в тёмной теме почти не перекрашивались. Список ручных
   `!important`-переопределений не покрывал `hover:` (наведение на строку давало
   светло-серую полосу), `amber/emerald/rose`-плашки (оставались яркими
   прямоугольниками) и большую часть рамок.
3. Полоса чёрного тонера (`bg-gray-800`) на тёмной дорожке была не видна: K
   выглядел пустым у каждого принтера.
4. 157 разрозненных `dark:`-классов в 13 компонентах.

Что сделано:

- **Графитовая нейтральная шкала** вместо синей. Четыре ступени поверхности
  (`#0f1115 → #15181e → #1b1f26 → #222730`), рамки — полупрозрачный свет, текст
  не доходит до чистого белого. Цвет оставлен только бренду и статусам.
- **Палитра Tailwind переопределена через CSS-переменные.** В Tailwind v4 каждая
  утилита читает цвет из `--color-*`. Файл `src/styles/palette-dark.css`
  (генерируется `frontend/scripts/gen-dark-palette.mjs`) переназначает их под
  `[data-theme="dark"]`. Нейтральные шкалы инвертируются на графитовую, у цветных
  светлые ступени становятся тонированными тёмными подложками, а тёмные — светлым
  текстом. Одним файлом перекрашены все `bg/text/border/ring/hover:` во всём
  приложении, без `!important`. Все `dark:`-классы удалены: поверх перекраски
  они бы её ломали.
- Цвета тонера, плитка недоступной кассы и цвет заголовка-магазина вынесены в токены.

После обновления Tailwind палитру нужно перегенерировать:
`node frontend/scripts/gen-dark-palette.mjs`.

### Производительность

- **framer-motion удалён.** Он подключался в `Layout`, то есть грузился на каждой
  странице (126 КБ, 41,6 КБ gzip), ради трёх эффектов: `scale(0.98)` при нажатии,
  подъёма карточки (уже был в CSS) и одного fade-in. Все три теперь на CSS.
- **Без `backdrop-filter` на непрозрачных панелях.** Размытия на сплошном фоне не
  видно, а каждой из десятков карточек доставался свой композитный слой и проход
  размытия на каждом кадре прокрутки.
- **События `invalidate` склеиваются.** Цикл опроса, массовая правка или
  перезагрузка точек присылают несколько событий подряд. Раньше каждая вкладка
  перезапрашивала весь список на каждое из них, теперь — один раз за 400 мс на список.

### Структура стилей

`index.css` (1090 строк) теперь только подключает модули `src/styles/`: `tokens`,
`palette-dark` (генерируется), `base`, `surfaces`, `status`, `tables`, `controls`,
`navigation`, `feedback`, `utility-mapping`, `motion` — в порядке каскада.

## 3. Рефакторинг крупных файлов

| Было | Стало |
|---|---|
| `app/services/cisco_ssh.py`, 1182 строки | пакет `cisco_ssh/`: `compat` (SHA-1 kex для старых IOS), `session` (`CiscoSSH`), `models`, `parsers` (чистые разборщики вывода IOS), `client` |
| `app/domains/remote_access/service.py`, 1338 строк | пакет `service/`: `devices`, `inventory`, `console`, `deployment`, `accounts`, `address_book` — без циклических импортов |
| `frontend/src/pages/CredentialsPage.tsx`, 763 строки, 9 компонентов | 12 строк страницы + `components/credentials/*` |
| `frontend/src/index.css`, 1090 строк | 11 модулей в `src/styles/` |

**`CiscoSwitchClient`.** Восемь операций принимали одни и те же пять аргументов
подключения (`ip, username, password, enable_password, port`) и повторяли один и
тот же каркас: открыть или переиспользовать сессию, посчитать метрику, закрыть.
Класс хранит подключение один раз, жизнью сессии управляют `_connected()` и
`_fresh()`. Три почти одинаковых помощника восстановления после сбоя записи
слились в один `_restore()`. Правило «порт, который уже погасили, обязательно
поднять обратно», метки метрик, тексты логов и последовательности команд
остались прежними. Функциональный API (`get_access_points(...)` и др.)
сохранён тонкими обёртками, поэтому вызывающий код не менялся.

**`remote_access/service`** — чистый перенос: тела всех функций и констант
совпадают со старыми на уровне AST. Модули отвечают четырём задачам из
docstring'а модуля. `service.<имя>` по-прежнему работает для всех вызывающих.

Почему не везде классы. Доменная логика удалённого доступа — функции без
состояния поверх `Session`. Обернуть их в класс значило бы переписать около 50
вызовов в тестах и коде, не получив ничего, кроме лишнего уровня отступа. Классы
введены там, где есть общее состояние или общие параметры: `CiscoSwitchClient`,
`EntityCache`.

## 5. Что не сделано и почему

- **Пакетная проверка circuit breaker'а** (`is_circuit_open` по одному запросу в
  Redis на устройство). Это 50–130 запросов по ~0,2 мс на фоне SNMP-таймаутов в
  секунды. Выигрыш незаметен, а тесты подменяют функцию поштучно.
- **87 `async`-роутов с синхронной сессией** (пункт 3.2 прошлого аудита). Решать
  по метрике `infrascope_event_loop_lag_seconds`, переписывать вслепую не стоит.
- **`RemoteAccessPage.tsx` (783 строки)** — один компонент с общим состоянием.
  Чтобы его разделить, состояние нужно поднять в хук. Это стоит делать вместе с
  следующей доработкой страницы, иначе есть риск регрессий.
- **Async-опрос свитчей** — см. `paramiko` выше.

## 6. Как проверить после выкатки

1. `docker compose logs backend | grep "alembic"` — применилась `926a321779de`.
2. `redis-cli --scan --pattern 'cache:*'` — по одному ключу на пространство имён
   (9 списков плюс по одному на свитч с недавно открытым списком портов), а не по
   ключу на каждый вариант фильтра и страницы.
3. Grafana → длительность `poll-all` принтеров на полном цикле: у парка с
   принтерами без веб-панели время должно уменьшиться.
4. Вкладка Network в браузере: на первой загрузке нет чанка `motion-*.js`.
5. Тёмная тема: страницы «Принтеры», «Обзор», «Кассы», «Удалённый доступ» — нет
   светлых плашек, у K видна полоса.

## 7. Инцидент при первой выкатке (28.10.2026, ~14:17 UTC)

Backend не поднялся: `prestart.sh` упал на `alembic upgrade head`, и контейнер
не прошёл healthcheck. Причин было две, обе внесены этими изменениями:

1. Из зависимостей удалили `asyncpg`: поиск использований шёл только по `app/`,
   а `alembic/env.py` подключается к базе именно через него.
2. Новой миграции дали id `d4e5f6a7b8c9`, который уже был занят
   (`add_connection_type_and_host_pc`). Alembic видит в этом цикл и не выполняет
   ни одной миграции.

Обе ошибки срабатывали до какого-либо DDL, поэтому база не изменилась.
Исправление: `asyncpg` и `greenlet` возвращены (asyncpg закреплён на прежней
0.31.0), миграции дан уникальный id `926a321779de`. Путь `prestart.sh` проверен на
чистом PostgreSQL под Python 3.14: все миграции с нуля, переход
`c1d2e3f4a5b6 → 926a321779de` и откат, `initial_data`, `/health`. Тест
`test_migrations.py` проверяет уникальность ревизий, единственный head,
отсутствие циклов и наличие драйвера миграций.

## 8. Вторая итерация: опрос и фронтенд (28.10.2026)

### Опрос

Длительность цикла ≈ ⌈устройств / параллельность⌉ × самое медленное устройство.
Оба множителя оказались больше, чем выглядели.

| Что | Было | Стало |
|---|---|---|
| Реальная параллельность TCP-проб (кассы, ПК, Iconbit, этикеточные) | 8: `asyncio.to_thread` упирался в пул по умолчанию `min(32, cpu+4)`, хотя в настройках стояло 16 | столько, сколько задано в настройках: пробы асинхронные, потоки не используют |
| Офлайн-касса (2 порта) | порты по очереди: ~7 с | все порты разом: ~3,5 с |
| Мёртвый принтер, SNMP до TCP-фолбэка | 5 с × 3 попытки = 15 с | 2 с × 2 = 4 с (`PRINTER_SNMP_*`) |
| Пул потоков для SSH/SNMP свитчей, ping, HTTP | 8 | 48 (`BLOCKING_IO_THREADS`) |
| Параллельность: принтеры / медиа / свитчи / ПК / кассы | 16 / 12 / 8 / 16 / 16 | 48 / 32 / 16 / 64 / 64 |
| Iconbit | новое TCP-соединение на каждый из 2–3 запросов статуса | общий клиент с keep-alive |

Оценка худшего случая (все устройства категории офлайн):

| Категория | Было | Стало |
|---|---|---|
| Кассы (80 шт.) | ~70 с (10 волн × 7 с) | ~7 с |
| Принтеры (52 шт.) | ~70–90 с | ~12 с |

Новая метрика `infrascope_snmp_poll_duration_seconds` показывает время опроса
каждого принтера.

**Важно для прода.** Если в `.env` заданы старые значения параллельности
(`PRINTER_POLL_MAX_WORKERS=16` и т.д. из прежнего README), новые значения по
умолчанию не применятся. Их нужно обновить или удалить из `.env`.

### Фронтенд

- Шрифт Inter теперь отдаётся с нашего сервера. Раньше страница ждала
  стилевой файл с fonts.googleapis.com, а это запрос через корпоративный шлюз.
  Внешних запросов при загрузке больше нет.
- Тема ставится до первой отрисовки: в тёмной теме больше нет белой вспышки.
- Чанки всех страниц предзагружаются в простое после входа. Переход между
  разделами на прод-сборке занимает 2–36 мс, спиннера маршрута нет.
