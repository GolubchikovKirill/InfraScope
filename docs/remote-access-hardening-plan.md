## Э0. Запустить Windows-агент (блокер всего остального)

Без него любой «Деплой» — это только строка в таблице. 93 задачи стоят
именно поэтому.

1. На доменной машине с правами на `\\host\C$` и `schtasks /S`
   развернуть `windows-rustdesk-agent/` (там `install-rustdesk-agent.cmd`).
2. `rustdesk-agent.json`: `server` — адрес InfraScope, `token` — значение
   `RUSTDESK_DEPLOY_AGENT_TOKEN` из серверного `.env`, `installer_dir` —
   сетевая шара с `rustdesk-1.4.9.exe`.
3. Убедиться, что в логах backend пошли `POST /api/v1/remote-access/agent/claim`.

Проверено вручную: эндпоинт отвечает 200 и отдаёт job с `id_server`,
`key`, `rustdesk_id` и флагами lockdown. Протокол рабочий.

## Э1. Честные статусы (главная причина «недостоверной информации»)

### 1.1 Не помечать `installing` при постановке в очередь
`service._enqueue_one()` ставит `dev.deploy_state = "installing"` в момент
создания задачи. Агента нет → 49 машин «устанавливаются» вечно, включая те,
где RustDesk уже стоит с ручной раскатки.

- Добавить состояние `queued` в `DEPLOY_STATES`.
- В `_enqueue_one` ставить `queued`, а `installing` — только в
  `report_job(status="running")` / при claim.
- Разово почистить прод: `installing` без claimed-задачи → `unknown`.

### 1.2 Развести «машина пингуется» и «RustDesk на связи»
`refresh_status_from_inventory()` пишет в `online`/`last_seen_at` результат
обычного пуллинга InfraScope. В UI это выглядит как «RustDesk онлайн».

- Разделить поля: `online` (только из консоли RustDesk) и
  `host_online`/`host_last_polled_at` (из инвентаря).
- В таблице и в `RemoteAccessButtons` показывать два разных индикатора,
  с подписями «хост» и «RustDesk».

### 1.3 Не врать про пароль
`has_password` — это «InfraScope знает пароль», а не «на машине задан
пароль». На машинах ручной раскатки пароль `kentdful` стоит, а флаг `false`.

- Переименовать в UI: «пароль в InfraScope: есть/нет».
- Отдельный признак «подтверждён агентом» (ставится в `report_job`).

### 1.4 Протухание задач
`reclaim_stale_jobs()` трогает только `claimed/running`. Задача в `queued`
может висеть вечно (сейчас — 93 штуки).

- Ввести TTL для `queued`: старше N часов → `failed` с понятным
  `result_detail` («агент не забрал задачу»).
- Показать на странице баннер «агент не отвечает N минут», если нет ни
  одного claim за окно.

## Э2. Книга адресов — то, чего ждёт пользователь

Сейчас `upsert_address_book_entry()` вызывается **только** из ручного
`POST /console/address-book`. Ни `prepare_device`, ни `enqueue` в консоль
не пишут. Поэтому после «Деплой компьютеры/неттопы» в клиенте пусто.

- В `prepare_device()` и в `report_job(status="done")` — пушить запись в
  книгу адресов: `id=rustdesk_id`, `alias=hostname`, теги по `source_kind`
  (`касса` / `пк` / `неттоп`) и по `location`.
- Кнопка на странице «Синхронизировать книгу адресов» — массовый upsert
  всех `managed` устройств.
- Учесть: в lejianwen книга адресов **пер-пользовательская**. Решить, под
  каким аккаунтом консоли пишем, и писать в shared-книгу с группой, иначе
  записи увидит только один пользователь. Это ключевой вопрос — уточнить
  у пользователя, под каким аккаунтом заходят техники.

## Э3. Починить пути консольного API (все текущие — угаданные)

Реальные маршруты, **снятые с живой консоли** (админский префикс
`/api/admin`, подтверждён из JS-бандла `/_admin/`; envelope
`{code,message,data}`, без токена отдаёт `code:403 "Please log in first"`):

| Наш код сейчас | Факт | Действие |
|---|---|---|
| `GET /api/user` | **404** | → `/api/admin/user/list` |
| `GET /api/audit/conn` | **404** (POST-only, это приём от клиентов) | → `/api/admin/audit_conn/list` |
| `GET /api/device` (fallback) | **404** | убрать, → `/api/admin/peer/list` |
| `GET /api/peers` | 401 — существует, но это *клиентский* API | → `/api/admin/peer/list` |
| `GET /api/ab` | 401 — существует, клиентский | → `/api/admin/address_book/list` |
| — | есть ещё `/api/admin/group/list`, `/api/admin/tag/list` | для тегов книги |

Важно: в консоли **две** сущности авторизации — клиентский API
(токен из `POST /api/login`) и админский (`/api/admin/*`). Панель
«Консоль RustDesk», которую я добавил, сейчас всегда покажет ошибку по
пользователям и подключениям даже с токеном — маршруты не те.

Порядок:
1. Пользователь генерирует токен в веб-консоли, кладёт в `.env`
   (`RUSTDESK_API_TOKEN`), рестарт `backend`+`worker`.
2. Временно `show-swagger: 1` в `~/rustdesk/conf/config.yaml` → сверить
   параметры (`page`/`page_size`, имена полей) → вернуть `0`.
3. Переписать `rustdesk_client.py` на `/api/admin/*`, добавить юнит-тесты
   с замоканным httpx на каждый метод.

## Э4. Надёжность очереди

- `claim_next_job()` без блокировки строки: два агента заберут одну задачу.
  Добавить `.with_for_update(skip_locked=True)`.
- Нет приоритета: сейчас `rotate_password` может уехать агенту раньше
  `deploy`, который ставит клиент. Сортировать по (приоритет действия,
  `created_at`); `deploy` → `reconfigure` → остальное.
- Задачи на офлайн-машину: не отдавать агенту, если `host_online=false`,
  либо помечать `deferred`, чтобы очередь не забивалась заведомо
  невыполнимым.
