# InfraScope: аудит платформы и план доработок (сентябрь 2026)

Снимок на 15.09.2026, ветка `v2/vnk_deploy` (`72b0044`). Всё ниже проверено:
по коду, локальным прогоном тестов и линтера, а на проде — только чтением
(`docker stats`, `psql` на SELECT, `.env` лишь на наличие флагов, без значений).

## Коротко

1. **Переписывать бэкенд на Go не нужно** — ни целиком, ни частично, по крайней
   мере сейчас. Python здесь не узкое место: CPU простаивает, а память уходит
   на инфраструктуру и на два конкретных дефекта, которые есть в любом языке.
   Go оставить там, где он уже работает правильно, — в агентах на конечных
   устройствах. Подробности и условия, при которых решение стоит пересмотреть, —
   в разделе «Go».
2. **Главный риск — не код, а эксплуатация**: у базы InfraScope нет бэкапа, на
   диске занято 85%, алерты никого не уведомляют, CI фактически не проверяет
   то, что уезжает на прод.
3. **Главный технический долг — лишняя сложность рантайма**: 17 контейнеров
   и около 9 ГБ RAM для ~370 устройств. «Микросервисы» собраны из одного образа
   и одного кода и ходят в одну БД. Kafka никто не читает.

## 2. Что сделано хорошо

Это стоит сохранить при любых изменениях:

- **Логика опроса, выстраданная инцидентами**: state machine подтверждения
  офлайна, circuit breaker с экспоненциальной паузой, эвристика «упала вся
  подсеть — это путь, а не устройства» (`printer_polling.py:86`,
  `switch_polling.py:70`), MAC-rediscovery.
- **Безопасные операции с железом**: лиз в Redis с compare-and-delete и
  маркером «уже пытались» для перезагрузки точек доступа (`worker/tasks.py:47`),
  отказ от автоповтора там, где он может перезагрузить AP дважды.
- **Классификация ошибок SSH** («неверный пароль» ≠ «недоступен»), совместимость
  со старыми Cisco, закрытие SNMP-движков после FD-утечки.
- **Шифрование секретов** в БД (Fernet + ротация ключей, `app/core/crypto.py`);
  на проде ключ задан.
- **Доменная раскладка** `app/domains/*` и тест границ слоёв; комментарии в коде
  объясняют «почему», а не «что».

Большая часть этой ценности — в знании предметной области, а не в синтаксисе.
Это главный аргумент против переписывания (см. раздел 4).

## 3. Проблемы по приоритету

### Критичные (закрыть в ближайшие дни)

**К1. У базы InfraScope нет бэкапа.** В crontab на сервере есть только
`rustdesk/backup.sh`. Дамп делается лишь перед `--reset-volumes`. В БД лежат
инвентарь, хранилище учётных данных (пароли от инфраструктуры) и журнал
событий. При потере диска всё это пропадёт. Отдельный риск:
`CREDENTIALS_ENCRYPTION_KEYS` хранится только в `.env` на том же диске.
Бэкап БД без ключа не расшифровать.

**К2. Диск занят на 85% и продолжает заполняться.** `docker system df`
показывает 22,9 ГБ неиспользуемых образов и 22,3 ГБ build cache — почти весь
диск. Каждый деплой добавляет ещё. Если закончится место, PostgreSQL
остановится. Метрик хоста (node-exporter) нет, поэтому заранее об этом никто
не узнает.

**К3. Алерты никого не уведомляют.** В `monitoring/prometheus/prometheus.yml`
нет секции `alerting`, Alertmanager отсутствует. В приложении тоже нет каналов
оповещения (Telegram, почта, вебхук). Правила в `infrascope-alerts.yml`
существуют, но увидеть их можно, только если открыть Prometheus UI вручную.

**К4. Неограниченный рост данных ML.** `train_toner_model` и
`train_offline_risk_model` (`app/ml/pipeline.py:66`, `:151`) при каждом
переобучении делают `SELECT` по всей таблице `mlfeaturesnapshot` в ORM-объекты.
Сейчас это 1,25 млн строк и 1,2 ГБ RSS; прирост ~7 млн строк в год. Таблица
занимает 95% БД и не очищается. В `mlmodelregistry` уже 604 версии моделей.
Итог — OOM и медленные дампы.

### Высокие (2–4 недели)

**В1. CI не защищает прод.** По `CLAUDE.md` коммиты доезжают до сервера и
дальше не идут, GitHub не обновляется, поэтому Actions не видят реальные
изменения. Даже если бы видели:
- `uv run pytest tests` (команда из `services/backend/service.yaml` и
  `scripts/quality-gate.sh`) **падает ещё на сборе тестов**: два файла с одним
  именем `tests/unit/services/test_honest_sign.py` и
  `tests/integration/api/test_honest_sign.py`, при этом `__init__.py` нет
  (`import file mismatch`);
- `ruff check` находит 3 ошибки (все исправляются через `--fix`);
- job «Backend Quality Baseline» гоняет лишь 6 выбранных файлов;
- матрица «по сервисам» запускает тесты одного и того же кода с разными
  фильтрами.

**В2. Тесты работают не на той БД и не на той версии Python.**
Интеграционные тесты идут на SQLite (`tests/conftest.py:36`), прод — на
PostgreSQL 17. Расхождения в регистронезависимом сравнении, JSON, `ON CONFLICT`
и блокировках тесты не поймают, а в недавних коммитах как раз чинили
регистронезависимый поиск по hostname. Python: локально и в CI 3.13
(`.python-version`), в прод-образе 3.14 (`Dockerfile:1`).

**В3. Kafka подключена, но не используется.** В коде нет ни одного
consumer'а; топик `infrascope.events` лишь дублирует `eventlog` в Postgres.
При этом бэкенд не стартует без healthy Kafka (`depends_on`). Стоимость —
~0,9 ГБ RAM, лишняя точка отказа и лишний сервис для обновлений.

**В4. У Jaeger нет лимита памяти.** `jaegertracing/all-in-one` без
`--memory.max-traces`; 2,45 ГБ за 4 недели работы.

**В5. «Микросервисы» без изоляции.** `polling-service`, `discovery-service`,
`network-control-service`, `ml-service` и `media-service` — это один образ,
один `app/`, одна БД и один `.env`. Цепочка для опроса принтеров:
beat → Celery worker (поток ждёт HTTP до 180 с) → `polling-service`
(HTTP-обработчик) → `asyncio.to_thread` → `ThreadPoolExecutor(16)` → в каждом
потоке `asyncio.run` с новым event loop → новый `SnmpEngine` на каждый запрос.
В `worker/tasks.py` у каждой задачи две ветки: через сервис и локально
(`if settings.POLLING_SERVICE_ENABLED`). В тестах проверяется одна, на проде
работает другая. Отдельный процесс оправдан только для `media-service`: он
единственный открыт наружу для клиентов в магазинах (`0.0.0.0:8014`).

### Средние (1–3 месяца)

**С1. Смешанная модель конкурентности.** 40 `async`-роутов используют
синхронную `Session` и блокируют event loop на время запросов к БД. В
`device_poll.py:638` и `snmp/poller.py:143` sync-обёртки поднимают поток
только ради `asyncio.run`. `SnmpEngine()` создаётся в 10 местах. Отсюда
утечки FD, которые чинили дважды, и дорогие циклы опроса.

**С2. Авторизация слабее, чем того требует хранилище паролей.**
Access-token живёт 7 дней (`config.py:62`) и лежит в `localStorage`
(`frontend/src/api/http.ts:16`), refresh — 30 дней, `AUTH_COOKIE_SECURE=false`.
На проде работает HTTP. Роль одна: `is_superuser`. Одна XSS или токен,
утёкший с рабочей станции, дают неделю доступа ко всем паролям инфраструктуры
и удалённому доступу.

**С3. 130 блоков `except Exception`.** Часть из них осознанные (fail-open для
локов опроса), часть скрывает ошибки. Например, `find_devices_by_macs` и
SNMP-хелперы молча возвращают `None`.

**С4. Два параллельных слоя**: `app/services/` (45 файлов) и `app/domains/`
(47 файлов), плюс фасады `app/models.py`, `app/crud.py`, `app/schemas.py`.
Миграция на домены не доведена до конца.

**С5. Шаблонный код в `worker/tasks.py`.** Каждая задача вручную повторяет
`_task_started`/`_task_finished` в try/except. Это место просится в
декоратор.

**С6. Нет сущности «Магазин».** `store_name` — строка на устройствах. Отчёты
вида «что сломано в магазине N», окна обслуживания по магазину и контакты
по магазину пока не на что опереть.

### Низкие / гигиена

- В git лежит бинарник `windows-media-agent/*.exe` (9 МБ). Его место —
  в релизах.
- В корне неотслеживаемый `dlg.dart` (88 КБ, файл из исходников клиента
  RustDesk). Скрипты `rustdesk-ksc/*.ps1` тоже не закоммичены.
- Образы с тегом `:latest`: prometheus, grafana, kafka-ui, blackbox-exporter.
  Поведение «обновились сами при pull» противоречит закреплению образов RustDesk.
- `pyrefly` (type checker) лежит в runtime-зависимостях (`pyproject.toml:39`)
  и попадает в прод-образ. Pyright настроен, но нигде не запускается.
- Скачивание `/assets/{asset_id}/file` в `media-service` не требует токен
  клиента (остальные ручки требуют). UUID в пути снижает риск, но это стоит
  сделать осознанным решением.
- 21 файл ручных API-клиентов во фронте (`frontend/src/api`) можно
  генерировать из OpenAPI.
- Большие страницы: `CredentialsPage.tsx` (751 строка),
  `RemoteAccessPage.tsx` (684).

## 4. Go: переписывать или нет

### Что даст Go

- Меньше памяти на процесс (десятки МБ против сотен).
- Горутины вместо `asyncio` + потоков + `asyncio.run`, одна модель
  конкурентности.
- Один статический бинарник без venv.
- `gosnmp` — зрелая и лёгкая библиотека, без проблем с жизненным циклом
  `SnmpEngine`.

### Почему это не решает реальные проблемы InfraScope

1. **Нагрузки нет.** ~370 устройств раз в 15 минут, цикл ≤ 60 с, CPU простаивает.
   Ускорять нечего.
2. **Память съедает не Python.** 3,4 ГБ приходится на Jaeger и Kafka,
   2,2 ГБ — на загрузку всей таблицы в ML и лишние процессы. После
   консолидации (фаза 2) Python-часть займёт ~1 ГБ. Переписывание на Go
   сэкономит ещё сотни МБ из 15 ГБ.
3. **Цена.** 25,5 тыс. строк, 168 эндпоинтов, 453 теста. Одному разработчику
   это 4–6 месяцев с заморозкой фич. Хуже, что придётся заново открывать
   правила, найденные в инцидентах: legacy KEX для Cisco, «упала подсеть, а
   не устройства», лизы перезагрузки AP, grace-период офлайна, классификация
   ошибок SSH.
4. **Экосистема для этой предметки в Python сильнее.** Работа с CLI сетевого
   железа (netmiko/scrapli), генерация Word для QR (`python-docx`), MSSQL
   для 1С (`python-tds`), быстрые правки ML/статистики. В Go для Cisco CLI
   придётся писать обвязку над `x/crypto/ssh` вручную или брать менее зрелый
   scrapligo, а для `.docx` хороших библиотек нет.
5. **Проблемы из раздела 3 от языка не зависят.** Бэкапы, диск, алерты, CI,
   рост таблицы и лишние сервисы остались бы и в Go.

### Где Go уместен

- **Агенты на конечных устройствах**, как уже сделанный `media-agent-go`.
  Если понадобится агент инвентаризации для компьютеров и касс (вместо
  NetBIOS и сканирования портов: железо, диски, аптайм, версия ПО кассы),
  писать его на Go. Это правильный инструмент для раскатки через Kaspersky SC.
- **Отдельный collector опроса на Go** — только при выполнении хотя бы одного
  условия:
  - устройств становится больше ~3–5 тыс.;
  - нужен интервал опроса ≤ 1 мин по всему парку;
  - после фазы 3 pysnmp продолжает ломаться на обновлениях.

  Схема на этот случай: collector пишет результаты в Postgres/Redis по
  контракту, API, UI и бизнес-логика остаются на Python.

**Вердикт:** не переписывать. Время лучше вложить в фазы 0–3 ниже. Решение
пересмотреть, когда выполнится любой из триггеров выше.

## 6. Что не проверялось

- Нагрузочное поведение UI и API: пользователей мало, отдельно не измерялось.
- Содержимое `.env` на проде, кроме флагов `*_ENABLED`, сроков жизни токенов
  и факта наличия ключа шифрования.
- Качество ML-прогнозов (используются ли они на практике) — стоит спросить
  пользователей, прежде чем вкладываться во что-то большее, чем retention.
- Фронтенд-тесты и e2e локально не запускались; `tsc --noEmit` проходит.
- Причина 30% CPU у `discovery-service` в момент первого замера: при повторной
  проверке процесс был в простое, скорее всего это был разовый скан.

Находки по ходу работы, не входившие в план:
- Корпоративный шлюз `vnk-srv-gate01` перехватывает исходящий HTTP (порт 80) с сервера и редиректит на страницу логина; HTTPS проходит. Это ломало `apt` при сборке образа. Канал с сервера наружу очень медленный.
- Тесты зависели от реального `.env` разработчика, реального DNS и Redis; фоновая задача `_persist_last_seen` открывала сессию к боевой БД мимо подмены зависимостей. Исправлено в `tests/conftest.py`.
- Redis-пул asyncio привязан к event loop: глобальный пул в Celery-задаче давал `Event loop is closed`. Теперь пул на каждый loop, `_run_async` закрывает его по завершении.
- Prometheus держал старый конфиг из-за bind-mount одиночного файла (inode); конфигурация монтируется каталогом.
- Консоль RustDesk хранит логины в нижнем регистре, из-за чего повторное создание учётки падало на UNIQUE.
